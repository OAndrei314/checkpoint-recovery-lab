# Checkpoint Recovery Lab

Replay a training job against a synthetic failure trace and compare checkpoint intervals.
The simulator separates useful work, discarded work, checkpoint overhead, and recovery time,
including failures that interrupt checkpoint writes or restart recovery itself.

Maintained by: claude-actions-daily-routine
Status: Active

## Quickstart

Python 3.10 or newer; no runtime dependencies, GPU, network, or API keys.

```sh
pip install -r requirements-dev.txt
pip install -e .
pytest -v
checkpoint-lab examples/training-job.json
checkpoint-lab examples/training-job.json --json
```

Use `python -m checkpoint_lab.cli` if the console script is not on your PATH.

## Model

All times are seconds. `useful_seconds` is the amount of uninterrupted compute needed to
finish the job. A checkpoint is scheduled after each `interval_seconds` of useful work.
It takes `checkpoint_seconds` to write and becomes durable only when the write finishes.
The simulator skips an unnecessary final checkpoint when useful work is complete.

Failures occur at the absolute wall-clock timestamps in `failure_times_seconds`:

- During compute: discard useful work since the last completed checkpoint.
- During a checkpoint: discard that partial write and all uncheckpointed useful work.
- During recovery: restart the full `recovery_seconds` duration.
- Exactly at a stage boundary: complete the stage first. A failure exactly at final job
  completion has no effect.

The initial state is a durable checkpoint at zero useful work. No failures occur after the
last listed timestamp. Input must be finite and nonnegative, with strictly increasing failure
times and positive work and interval durations. Every replay accounts for:

```
total time = useful work + discarded work + checkpoint time + recovery time
```

For example, with 100 seconds of work, interval 30, checkpoint time 5, recovery time 10,
and a failure at time 40: the first checkpoint finishes at 35; five seconds of work are lost;
recovery ends at 50; the job finishes at 130. Tests check this example and failures during
writes and repeated recovery, plus conservation of elapsed time over 200 seeded traces.

## Reproduced example

`examples/training-job.json` contains eight hours of useful work, 45-second checkpoints,
120-second recovery, and seven explicitly listed synthetic failures. The checked-in
`examples/results.json` was generated by the CLI from that exact input.

| Interval (s) | Completion time (s) | Discarded work (s) | Checkpoint time (s) | Recovery time (s) |
| ---: | ---: | ---: | ---: | ---: |
| 480 | 33,800 | 1,505 | 2,655 | 840 |
| 960 | 35,285 | 4,310 | 1,335 | 840 |
| 240 | 36,125 | 1,090 | 5,395 | 840 |
| 1,920 | 39,170 | 8,900 | 630 | 840 |
| 120 | 40,865 | 433 | 10,792 | 840 |
| 3,840 | 46,895 | 16,940 | 315 | 840 |
| 60 | 51,545 | 267 | 21,638 | 840 |

These are simulated accounting results, not measured GPU performance. The 480-second
interval wins among these candidates on this trace; it is not a general optimal policy.
Choosing a production interval needs independent traces and measurements of actual storage,
restart, and compute behavior. Fixed failure timestamps let each policy see the same external
events, although longer runs may encounter additional failures before completion.

## Status / next steps

Working replay engine, JSON/table CLI, reproducible example, and offline tests. Next work:
train/held-out trace evaluation, variable checkpoint costs, and incremental checkpoint
policies. The current model has one job, one durable checkpoint location, and constant costs.
It does not model checkpoint corruption, asynchronous writes, distributed ranks, correlated
hardware faults, or changing compute throughput. All data is synthetic and created from
scratch; no proprietary data, algorithms, or hardware measurements are involved.
